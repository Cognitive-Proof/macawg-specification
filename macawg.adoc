== Abstract

This document defines Macawg, a protocol that lets a C2PA claim generator obtain an identity assertion `signature` from a credential holder's wallet.
The claim generator builds a request that contains the CAWG `signer_payload` and the identities it wants, signs the request with its C2PA signing certificate, and offers it to the wallet through an invite URI, normally shown as a QR code.
The wallet verifies the request, obtains a signature (for identity claims aggregation, from a third-party issuer), and returns it.
The claim generator verifies the response before it places the signature in the identity assertion.

Macawg is a companion to the {cawg-ia}[CAWG Identity Assertion specification, version 1.3].
That specification defines the assertion and its signature types.
This document defines how the signature travels between the two parties.

[NOTE]
.Status of this document
====
This is a draft, not a CAWG work product.
The Rust crate https://github.com/Cognitive-Proof/macawg[`macawg`] 0.2.0 is its reference implementation.
Each normative rule either traces to that crate or is marked *(proposed)*.
A proposed rule is part of the intended protocol, but the reference implementation does not enforce it yet.
Where this document names a crate function, the name is informative.

The document separates the CAWG signing operation (<<operation>>) from the bindings that carry it.
Binding A, the Macawg COSE/HTTPS exchange, is normative and implemented.
Bindings B (OpenID4VCI issuance), C (OpenID4VP) and D (CSC) are proposed, and none is implemented (<<bindings>>, <<recommendation>>).
====

== Introduction

=== Scope

The CAWG Identity Assertion specification (§6.1) requires that the `signer_payload` "MUST be presented to be signed by the credential holder", and §8.1 says that an identity claims aggregator issues the credential that becomes the `signature` value.
It does not say how the payload reaches the credential holder or how the signature comes back.
Each implementation must therefore invent its own exchange, and wallets and devices from different vendors cannot work together.

This document fills that gap for the case where the identity assertion generator and the credential holder are on different devices.
For example, the generator might be a camera and the holder a person's phone.
It specifies:

* the CAWG signing operation: its inputs, its result, and the guarantees every binding must give (<<operation>>);
* binding A, the normative exchange: an invite URI, a COSE-signed request, wallet checks, a response, device checks, and HTTPS transport (<<binding-a>>);
* how the wallet produces the signature in each mode (<<ica>>, <<x509>>);
* proposed alternative bindings: OpenID4VCI issuance of ICA credentials (<<binding-b>>), OpenID4VP for the device-to-wallet exchange (<<binding-c>>), and CSC remote X.509 signing (<<binding-d>>).

The following are out of scope:

* the identity assertion itself, its CBOR encoding, and how a validator checks it ({cawg-ia}[CAWG Identity Assertion] §5–§8);
* how an identity claims aggregator verifies a person's identities (for example, through OAuth);
* any wallet-to-issuer interface other than binding B, which is proposed;
* rendering of QR codes and the user interface of the wallet.

=== Conceptual overview

[source]
----
claim generator                     wallet                         ICA issuer
───────────────                     ──────                         ──────────
build request (signer_payload,
  requested identities)
sign request (C2PA cert, COSE)
show invite  ──── QR: macawg:// ──▶ parse invite
             ◀─── GET request ───── verify request     
                                    ask the person
                                    build unsigned credential ───▶ verify identities
                                                                   issue COSE_Sign1
             ◀─── POST response ─── build response         ◀────── signature
verify response
signature → cawg.identity assertion
----

The flow has three properties:

. The person scans a code, normally shown by the device.
The nonce in that code ties the request the wallet fetches, and the response the device receives, to possession of that invitation.
Possession of an invitation does not prove physical proximity to the device (<<relay>>).
. The request is signed with the same credential the generator uses to sign the C2PA claim.
A wallet can therefore tell the person which C2PA signer is asking, and check that signer against the C2PA trust list.
. For `cawg.identity_claims_aggregation`, the wallet does not sign.
A third-party issuer that has verified the identities signs the credential.
The `c2paAsset` in that credential binds it to the assertions that the `signer_payload` references, including the claim's hard binding (<<binding-scope>>).

== Terms and definitions

=== Concepts adapted from the CAWG Identity Assertion specification

==== Identity assertion generator

The actor that builds the identity assertion and places it in a C2PA claim.
In this document, the identity assertion generator is also the C2PA claim generator, and is called the *device*.

Adapted from <<CAWG-IA>> §3.

==== Credential holder

The person, and the software acting for them, that controls the credential used to sign the `signer_payload`.
In this document, the software is called the *wallet*.

Adapted from <<CAWG-IA>> §3.

==== Identity claims aggregator

A third party that verifies a person's identities and issues an `IdentityClaimsAggregationCredential` that names them.
In this document, it is called the *ICA issuer*.

Adapted from <<CAWG-IA>> §8.1.

==== Signer payload

The `signer_payload` data structure defined in <<CAWG-IA>> §5.2.
In this document, it means the payload the device computed for one claim.

=== Terms defined by this document

==== Session

One run of the protocol, from showing an invite to accepting or rejecting a response.
A session is named by a session id and secured by a nonce.

==== Invite

A URI with the `macawg` scheme that tells the wallet how to reach a session (<<invite>>).

==== Sign request

The JSON object, of type `macawg.sign_request`, that describes what the device asks the wallet to sign (<<request>>).

==== Request envelope

The sign request bytes together with a detached `COSE_Sign1` over them (<<request-auth>>).

==== Sign response

The JSON object, of type `macawg.sign_response`, that carries the wallet's signature or its refusal (<<response>>).

==== Unsigned ICA credential

The information a wallet gives an ICA issuer so that the issuer can produce a credential for one request (<<ica>>).

==== Requester

The holder of the C2PA signing certificate that signed a request envelope.

==== Operation

The CAWG signing operation of <<operation>>, independent of any encoding.

==== Binding

A definition of how the operation's inputs and result are encoded and carried, and how its guarantees are met (<<bindings>>).

==== Request representation

The exact octets that a binding defines as the request, over which the response proof's `request_digest` is computed (<<proof-domains>>).

=== Data encodings

base64url::
Base64 with the URL and filename safe alphabet, without padding (<<RFC4648>> §5).
Unless this document says otherwise, binary values in JSON are base64url strings.
Receivers SHOULD also accept padded base64url and standard base64 (<<RFC4648>> §4).
_(Traces to `Base64Bytes`.)_

Timestamp::
A JSON string in the format of <<RFC3339>>, in UTC.

== Standard terms

The key words "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL NOT", "SHOULD", "SHOULD NOT", "RECOMMENDED", "NOT RECOMMENDED", "MAY", and "OPTIONAL" in this document are to be interpreted as described in BCP 14 <<RFC2119>> <<RFC8174>> when, and only when, they appear in all capitals, as shown here.

A rule marked *(proposed)* is normative for this draft, but the reference implementation does not yet enforce it.
This includes rules about user interface, deployment policy and session state, which a stateless library cannot enforce and which the application that embeds it must carry out.

== Actors and protocol version

=== Actors

Device::
The C2PA claim generator, which is also the identity assertion generator.
It holds a C2PA signing credential: an X.509 certificate chain that meets the C2PA certificate profile, and its private key.
It computes the `signer_payload`, starts the session, and puts the returned signature into the identity assertion.

Wallet::
Software that acts for the credential holder.
It reads the invite, verifies the request, shows the request to the person, and returns a response.
For `cawg.x509.cose`, the wallet holds the person's X.509 credential and signs.
For `cawg.identity_claims_aggregation`, the wallet holds the person's verified identities, or references to them, and obtains the credential from an ICA issuer.

ICA issuer::
An identity claims aggregator.
It signs `IdentityClaimsAggregationCredential` credentials with an Ed25519 key named by a DID.

=== Protocol version

This document defines protocol version `1`.
The invite, the sign request, and the sign response each carry the version.
A receiver MUST reject a message whose version it does not support.
_(Traces to `Invite::parse`, `check_request`, `check_response`.)_

=== Signature types

A session asks for exactly one of these `sig_type` values, defined in <<CAWG-IA>> §8:

* `cawg.identity_claims_aggregation` (§8.1);
* `cawg.x509.cose` (§8.2).

A wallet MUST reject a request for any other `sig_type`.
_(Traces to `check_request`.)_

[[operation]]
== The CAWG signing operation

Macawg defines one operation, and carries it over one or more _bindings_.
The operation says what is being approved and what each party must check.
A binding says how the operation's inputs and result are encoded and transported, and how the guarantees below are achieved with that encoding.

Binding A (<<binding-a>>), the Macawg COSE/HTTPS exchange, is the normative binding of this draft.
The other bindings are proposed, and are described separately in <<binding-b>>, <<binding-c>> and <<binding-d>>.

[[operation-inputs]]
=== Inputs

[cols="2,4,2",options="header"]
|===
|Input |Meaning |Binding A member

|Signer payload |The exact CAWG `signer_payload` to be signed (<<CAWG-IA>> §5.2). |`signer_payload`
|Mode |`cawg.identity_claims_aggregation` or `cawg.x509.cose` (<<_signature_types>>). |`signer_payload.sig_type`
|Claim generator credential |The C2PA signing certificate chain that authenticates the request, and that will sign the claim. |`x5chain` of the request `COSE_Sign1`
|Requested disclosures |Identity types, fields and providers the device asks for. ICA mode only. |`requested.identities`
|Accepted issuers |ICA issuer DIDs the device accepts. ICA mode only. |`requested.accepted_issuers`
|Maximum signature size |Space reserved for the identity assertion's `signature`. |`max_signature_size`
|Proof requirement |Whether a request-to-result proof is mandatory (<<response-proof>>). |`response_proof_required`
|Deadline |`issued_at` and `expires_at`, giving the acceptance deadline (<<acceptance-deadline>>). |`issued_at`, `expires_at`
|Invitation values |Session id, nonce and the session's endpoint. |`session_id`, `nonce`, `session_url`
|Display context |The requester's description of the content. Not security-relevant. |`context`
|===

[[operation-result]]
=== Result

The result is one of:

Signed::
The exact bytes for the identity assertion's `signature` field, and, when present, a response proof over the request and those bytes.

Declined::
No signature, with an optional reason.
The reason `response_proof_unsupported` means the wallet could not produce a required proof.

[[guarantees]]
=== Guarantees

Every binding MUST provide each of these guarantees.
A binding that cannot provide one MUST say so, and MUST NOT be described as conforming for that mode.
The section references give the binding A rules.

[cols="1,3,5,2",options="header"]
|===
|Id |Guarantee |Requirement |Binding A

|G1 |Claim generator authentication |The request is integrity-protected and signed with the claim generator's C2PA signing credential. The wallet validates the certificate profile and, in production, the C2PA trust list. |<<request-auth>>, <<trust-modes>>
|G2 |_Withdrawn_ |Was: `expected_claim_generator` identifies the certificate that authenticated the request. Withdrawn in 0.6, because <<CAWG-IA>> 1.3 removed the field (<<claim-generator-substitution>>). The number is kept so that G3 to G12 do not change. |—
|G3 |Invitation binding |The request is bound to the scanned invitation, and the response goes only to the destination named in the signed request, with no redirects. |<<_nonce_binding>>, <<transport-https>>
|G4 |Exact payload |The wallet signs, or has issued, exactly the signer payload in the request. Unknown payload members are rejected, never dropped. |<<wire-signer-payload>>, <<extensions>>
|G5 |Disclosure control |Only requested types, fields and providers; exactly the values the person approved; no other property, header or entry. The wallet checks before release. |<<selective-disclosure>>, <<wallet-release>>
|G6 |Informed approval |The person sees the requester, the context as the requester's description, the roles, and the identity values and their publication, and agrees. |<<wallet-validation>>
|G7 |Issuer acceptance |An ICA credential's issuer is in `accepted_issuers`, or allowed by an independent trust policy, and the credential is valid. |<<device-ica>>
|G8 |Size |The signature fits `max_signature_size`. All inputs are within the maximums. |<<resource-limits>>
|G9 |Exact bytes |The `signature` bytes travel unchanged from the signer to the identity assertion. Nobody repairs or rewrites them. |<<_use_of_the_signature>>
|G10 |Request-to-result proof |When required, the key that made the identity signature also signs a digest of the exact request and a digest of the exact signature bytes. For ICA, the issuer signs only under current actor authorization. |<<response-proof>>
|G11 |Deadline |One acceptance deadline applies to every party. |<<acceptance-deadline>>
|G12 |Fail-closed extensions |A receiver that does not implement a security-relevant requirement rejects the request; it does not ignore the requirement. |<<extensions>>
|===

These properties are separate and must not be confused:

Session correlation::
A response names the session it belongs to (`session_id`, `nonce`, or OpenID4VP `state`). It proves nothing by itself.
Holder-key possession::
A key that a credential is bound to signs something. In ICA mode, Macawg has no holder key.
Transaction authorization::
The actor approves specific transaction data. In ICA mode this happens at the issuer (<<_producing_a_proof_for_ica>>).
Issuer attestation::
The ICA issuer signs the identities and the `c2paAsset`. This is what the asset publishes.

G10 combines transaction authorization with a binding to the exact result.
None of the other three provides it alone.

[[proof-domains]]
=== Request digest and proof domains

The response proof payload is the same in every binding: the CBOR map `{ "request_digest": bstr, "signature_digest": bstr }` (<<response-proof>>).
What a binding must define is its _request representation_, the exact octets that `request_digest` is computed over, and its external AAD.

[cols="2,4,3,2",options="header"]
|===
|Binding |Request representation |External AAD |Status

|A, COSE/HTTPS |The octets of the decoded envelope `request` member: the UTF-8 JSON exactly as signed. |`macawg.sign_response.v1` |Implemented
|C, OpenID4VP |The octets of the Request Object, in JWS compact serialization, exactly as received from `request_uri`, before any decoding. |`macawg.sign_response.oid4vp.v1` *(proposed)* |Not implemented
|===

Binding B is not device-facing.
It carries the device-facing binding's request digest and AAD to the issuer, unchanged (<<vci-dataset>>).
Binding D is wallet-internal and uses the device-facing binding's values.

These rules apply to every binding:

* `request_digest` MUST be computed over the octets the device signed or served, as received. It MUST NOT be computed over JSON or claims that were parsed and serialized again.
* Each binding MUST use its own external AAD, so that a proof made for one binding does not verify in another.
* A new binding, or a change to a binding's request representation, MUST define a new AAD string.

[[bindings]]
=== Bindings and their status

[cols="2,2,2,3",options="header"]
|===
|Binding |Between |Status |Implementation

|A, Macawg COSE/HTTPS (<<binding-a>>) |Device and wallet |Normative |macawg 0.2.0
|Local-key X.509 signing (<<x509>>) |Inside the wallet |Normative |macawg 0.2.0 (`x509` feature)
|B, OpenID4VCI ICA issuance (<<binding-b>>) |Wallet and ICA issuer |Proposed |Not implemented
|C, OpenID4VP (<<binding-c>>) |Device and wallet |Proposed, evaluation only |Not implemented
|D, CSC `signHash` remote signing (<<binding-d>>) |Wallet and RSSP |Proposed, ES* and PS* only |Not implemented
|D, CSC Data Model Bindings profile (<<binding-d-dmb>>) |Device and wallet, over OpenID4VP |Informative evaluation |Not implemented
|===

Bindings compose: a device and wallet use A (or C), and the wallet may use B with its ICA issuer, or D with an RSSP.

[[binding-a]]
== Binding A: Macawg COSE/HTTPS

Binding A carries the operation as a COSE-signed JSON request, fetched over HTTPS after the wallet scans an invite, and a JSON response posted back to the same URL.
It is the normative binding of this draft, and the one the reference implementation implements.

The sections from <<invite>> to <<transport>> define binding A.
<<ica>> and <<x509>> also define how the wallet produces the signature in each mode; binding B and binding D are alternatives for those wallet-side steps.

[[invite]]
== Invite URI

=== Syntax

An invite is an absolute URI <<RFC3986>> with the scheme `macawg` and the authority `sign`.
Its parameters are carried in the query component:

[source]
----
macawg://sign?v=1&sid=<session id>&n=<nonce>&t=https&u=<session URL>
macawg://sign?v=1&sid=<session id>&n=<nonce>&t=ble&svc=<service UUID>[&name=<local name>]
----

[cols="1,1,4",options="header"]
|===
|Parameter |Presence |Meaning

|`v` |REQUIRED |Protocol version, a decimal integer. `1` for this document.
|`sid` |REQUIRED |Session id.
|`n` |REQUIRED |Session nonce.
|`t` |REQUIRED |Transport: `https` or `ble`.
|`u` |REQUIRED when `t=https` |The session URL (<<transport-https>>).
|`svc` |REQUIRED when `t=ble` |BLE GATT service UUID (<<transport-ble>>).
|`name` |OPTIONAL, `t=ble` only |BLE local name, to help the wallet pick a peripheral.
|===

Parameter values MUST be percent-encoded as `application/x-www-form-urlencoded` query values.
_(Traces to `Invite::to_uri`.)_

=== Session id and nonce

*(proposed)* The device MUST generate a fresh session id and a fresh nonce for each session.
The nonce MUST be unpredictable to anyone who has not seen the invite.

*(proposed)* The nonce MUST contain at least 128 bits of entropy from a cryptographically secure random number generator, and SHOULD be encoded as base64url.
The reference implementation provides `random_token(16)`, which meets this requirement, but it does not enforce a minimum for nonces that applications supply.

=== Parsing

A wallet parsing an invite:

. MUST reject a URI whose scheme is not `macawg`.
. MUST reject an invite that is missing `v`, `sid`, `n` or `t`, or is missing the parameters that its transport requires.
. MUST reject an invite whose `v` it does not support.
. MUST reject an invite whose `t` it does not support.
. For `t=https`, MUST reject a `u` that is not an `http` or `https` URL.

_(Traces to `Invite::parse`.)_

*(proposed)* Outside of development, a wallet MUST reject a `u` whose scheme is `http`.
The reference implementation accepts `http` so that devices on a local network can be tested without TLS certificates.

A wallet MUST NOT treat a parsed invite as evidence of who the requester is.
Anyone can show a QR code.
The requester is established only by <<request-auth>>.

[[request]]
== Sign request

=== Structure

A sign request is a JSON object <<RFC8259>> with these members:

[cols="2,1,5",options="header"]
|===
|Member |Presence |Meaning

|`type` |REQUIRED |The string `macawg.sign_request`.
|`version` |REQUIRED |The protocol version, `1`.
|`session_id` |REQUIRED |MUST equal the invite's `sid`. 16 to 64 characters from the base64url alphabet (<<field-lengths>>).
|`session_url` |REQUIRED for HTTPS |The session URL. MUST equal the invite's `u` (<<transport-https>>).
|`nonce` |REQUIRED |MUST equal the invite's `n`. 16 to 64 characters from the base64url alphabet (<<field-lengths>>).
|`issued_at` |REQUIRED |Timestamp when the device created the request.
|`expires_at` |REQUIRED |The nominal expiry. The request may be acted on until the acceptance deadline (<<acceptance-deadline>>), and not after.
|`signer_payload` |REQUIRED |The signer payload to sign (<<wire-signer-payload>>).
|`max_signature_size` |REQUIRED |The number of bytes the device reserved for the identity assertion's `signature` field. A positive integer.
|`requested` |OPTIONAL |The identities the device asks for (<<requested>>). Absent means the wallet chooses.
|`context` |OPTIONAL |Descriptive information for display (<<request-context>>).
|`response_proof_required` |OPTIONAL |Boolean, default `false`. When `true`, the device will accept a `signed` response only with a valid `response_proof` (<<response-proof>>).
|`crit` |OPTIONAL |Array of top-level member names that the receiver MUST understand (<<extensions>>).
|===

[[extensions]]
=== Unknown members and extensions

All the members this document defines are part of protocol version 1, including the ones marked proposed.
A receiver that conforms to this document recognises every one of them.

Top level and `context`::
A receiver MUST ignore a member it does not recognise, unless the member is named in `crit`.
A device MUST NOT rely on a receiver enforcing a member that is not defined in this document, unless it names that member in `crit`.
An ignored member therefore cannot weaken any check this document defines.
_(Ignoring traces to the serde definitions, which do not deny unknown fields.)_

`crit`::
If `crit` is present, the receiver MUST reject the request unless it recognises and implements every member named in it.
`crit` MUST NOT be empty, and MUST NOT name a member that is absent.
Future security-relevant extensions MUST be listed in `crit`, or introduced with a new protocol version.
_(Traces to `check_crit` and `REQUEST_MEMBERS`, called from `seal_request` and `open_request`. Presence is read from the request bytes as signed.)_

`signer_payload`::
A receiver MUST reject a request whose `signer_payload` contains a member it does not recognise, and MUST NOT remove such a member.
Members of `signer_payload` restrict what the identity signature means.
A receiver that dropped one would either sign a weaker statement than the device asked for, or return a payload that fails the device's equality check.
_(Traces to `WireSignerPayload` and `WireHashedUri`, which deny unknown fields.)_

NOTE: `crit` protects only against receivers that implement it.
Version 0.1.0 of the reference implementation dropped unknown `signer_payload` members and ignored `crit`.

[[wire-signer-payload]]
=== `signer_payload`

The `signer_payload` member is the JSON form of the CBOR `signer_payload` map in <<CAWG-IA>> §5.2:

[cols="2,1,5",options="header"]
|===
|Member |Presence |Meaning

|`referenced_assertions` |REQUIRED |Array of hashed URIs. Each has `url` (string), `alg` (string, OPTIONAL), and `hash` (base64url).
|`sig_type` |REQUIRED |One of the values in <<_signature_types>>.
|`role` |OPTIONAL |Array of role strings. Omitted when empty.
|===

The device MUST produce `signer_payload` from the same payload that it will place in the identity assertion, so that converting it back to CBOR yields the same map.
_(Traces to `WireSignerPayload` and its `From` conversions.)_

The `referenced_assertions` MUST include the claim's hard binding assertion, as <<CAWG-IA>> §5.2 requires.
A wallet MUST reject a request in which no entry's URL has a last path segment that begins with `c2pa.hash.`.
_(Traces to `WireSignerPayload::has_hard_binding`.)_

This check is syntactic.
It catches a device that forgot the hard binding, but the wallet cannot see the claim, so it cannot confirm that the reference names a valid, active hard binding assertion.
Validators of the asset make that check (<<CAWG-IA>> §7).

[[expected-members]]
==== `expected_*` members are not permitted

Version 1.2 of <<CAWG-IA>> defined three optional members, `expected_partial_claim`, `expected_claim_generator` and `expected_countersigners`.
Version 1.3 removed them, and says validators MUST ignore them (<<CAWG-IA>> §5.1).
A member that validators ignore protects nothing, so Macawg does not use them.

A device MUST NOT include any of them in `signer_payload`.
A wallet receives them as unknown `signer_payload` members, and so MUST reject the request (<<extensions>>, G4, G12).
_(Traces to `WireSignerPayload`, which denies unknown members.)_

[[requested]]
=== `requested`

The `requested` member says which identities the device wants in an ICA credential.
It MUST be absent unless `signer_payload.sig_type` is `cawg.identity_claims_aggregation`.
_(Traces to `seal::validate`.)_

[cols="2,1,5",options="header"]
|===
|Member |Presence |Meaning

|`identities` |REQUIRED |Array of identity requests.
|`accepted_issuers` |OPTIONAL |Array of DIDs, without fragments, of the ICA issuers the device accepts. Absent or empty means any issuer.
|===

Each identity request has these members:

[cols="2,1,5",options="header"]
|===
|Member |Presence |Meaning

|`type` |REQUIRED |A `verifiedIdentities[].type` value from <<CAWG-IA>> §8.1: `cawg.document_verification`, `cawg.web_site`, `cawg.affiliation`, `cawg.social_media`, or `cawg.crypto_wallet`.
|`required` |OPTIONAL |Boolean, default `false`. When `true`, a response without an identity of this type MUST be rejected.
|`fields` |REQUIRED |Array of field names to disclose: any of `name`, `username`, `address`, `uri`.
|`providers` |OPTIONAL |Array of accepted `provider.id` URIs. Absent or empty means any provider.
|`purpose` |OPTIONAL |Text that explains to the person why the device asks.
|===

A `requested` member is well-formed only if all of these hold:

. Every `type` is one of the five values above.
. No `type` appears in more than one identity request.
. `fields` includes the mandatory field for the type shown in <<mandatory-fields>>.

The device MUST NOT send a request with a malformed `requested`, and a wallet MUST reject one.
_(Traces to `Requested::validate`, called from `seal_request` and `open_request`.)_

[[mandatory-fields]]
.Mandatory field per identity type
[cols="2,1,2",options="header"]
|===
|Type |Mandatory field |Source
|`cawg.document_verification` |`name` |<<CAWG-IA>> §8.1
|`cawg.affiliation` |`name` |Macawg restriction
|`cawg.social_media` |`username` |<<CAWG-IA>> §8.1
|`cawg.crypto_wallet` |`address` |<<CAWG-IA>> §8.1
|`cawg.web_site` |`uri` |<<CAWG-IA>> §8.1
|===

<<CAWG-IA>> does not require `name` for `cawg.affiliation`.
Macawg adds the requirement, so that each disclosed identity includes at least one field that identifies the named actor.
<<CAWG-IA>> makes such a field mandatory for every other type, and for an affiliation the only one is `name`.
_(Traces to `IdentityField::mandatory_for`.)_

In <<CAWG-IA>> §8.1, `verifiedIdentities[].name` is the named actor's own name, as the identity provider understands it.
The organization that the actor belongs to is described by `provider`.
A wallet or issuer MUST NOT put the organization's name in `name` when the named actor is a person.

NOTE: Open question.
This restriction rules out an anonymous disclosure such as "a member of organization X".
Reviewers may prefer to drop it and follow <<CAWG-IA>>.

[[selective-disclosure]]
==== Matching identities to a request

A list of verified identities _answers_ a `requested` member when all of these hold:

. The type of every identity appears in `requested.identities`.
. Each type appears at most once.
. For each identity, every field in its request's `fields` is present and non-empty.
. For each identity, none of the selectable fields (`name`, `username`, `address`, `uri`) is present unless it is in its request's `fields`. The members `type`, `verifiedAt` and `provider` are always present, and are not selectable.
. If the identity request has a non-empty `providers`, the identity's `provider.id` is in it.
. Every identity request with `required: true` has a matching identity.

_(Traces to `Requested::check`.)_

Rule 4 is deliberate.
The wallet discloses exactly the fields the device asked for, and no more.
A device that wants a field must ask for it.

[[request-context]]
=== `context`

The `context` member describes the content for display to the person.
It is covered by the request signature, but it is descriptive: the binding to the content is the `signer_payload`.
All members are OPTIONAL.

[cols="2,5",options="header"]
|===
|Member |Meaning
|`claim_generator` |Name of the claim generator.
|`title` |Title of the asset.
|`format` |Media type of the asset.
|`thumbnail` |Object with `format` (media type) and `data` (base64url).
|`assertions` |Array of objects with `label` and an OPTIONAL `summary`, which describe the referenced assertions.
|`message` |Free text for the person.
|===

A wallet MUST NOT rely on `context` for any security decision.
_(No check in the reference implementation reads `context`.)_

The request signature shows which requester supplied the `context`.
It does not show that a thumbnail or title depicts the content that the `signer_payload` hashes identify.
A wallet SHOULD present `context` as the requester's description, not as a verified view of the content.

[[request-auth]]
== Request authentication

=== Request envelope

The device MUST sign each request with its C2PA signing credential, the same credential that it uses to sign the C2PA claim.
The wallet fetches a request envelope, a JSON object with these members:

[cols="2,1,5",options="header"]
|===
|Member |Presence |Meaning
|`request` |REQUIRED |base64url of the UTF-8 JSON bytes of the sign request, exactly as signed.
|`cose_sign1` |REQUIRED |base64url of a tagged `COSE_Sign1` <<RFC9052>> with a detached payload.
|===

The wallet MUST verify the signature over the decoded `request` bytes, and MUST parse the request from those same bytes.
It MUST NOT re-serialise the request before verifying it.
_(Traces to `RequestEnvelope`, `open_request`.)_

=== `COSE_Sign1` construction

The device MUST construct the `COSE_Sign1` as follows:

. The protected header MUST contain:
.. `alg` (label 1): the COSE algorithm of the signing key. One of ES256, ES384, ES512, PS256, PS384, PS512, or EdDSA (Ed25519), as allowed by <<C2PA>> for claim signatures.
.. `content type` (label 3): the text string `application/vnd.macawg.sign-request+json`.
.. `x5chain` (label 33, <<RFC9360>>): the signing certificate chain, end-entity certificate first. A chain of one certificate is a single byte string. A longer chain is an array of byte strings.
. The payload MUST be detached (`nil`).
. The external AAD MUST be the 22 ASCII bytes `macawg.sign_request.v1`.
. The signature is computed over the `Sig_structure` of <<RFC9052>> §4.4 with context `"Signature1"`, the protected header, the external AAD above, and the request bytes as payload.

_(Traces to `seal_request`, `REQUEST_AAD`, `REQUEST_CONTENT_TYPE`.)_

The external AAD separates request signatures from every other use of the C2PA credential.
A request signature cannot be presented as a C2PA claim signature, nor the reverse.

=== Nonce binding

The request carries the session id and nonce from the invite, and both are under the device's signature.
The wallet MUST check that they equal the values in the invite it scanned (<<wallet-validation>>).

This proves that the request was signed for the session named in the invite the person scanned.
A request captured from another session does not carry the right nonce.
It does not prove that the wallet fetched the request directly from the device: an attacker can relay the device's own signed request (<<relay>>).

The wallet MUST also check that `session_url` equals the invite's `u`, using the comparison in <<url-comparison>>.
_(Traces to `check_request`.)_
*(proposed)* The wallet MUST send the response only to `session_url`, following the redirect rules in <<transport-https>>.
The reference implementation leaves HTTP to the application, so the application must enforce this rule.
This stops an attacker from showing an invite that points to their own proxy, relaying the device's request through it, and collecting the response.

[[trust-modes]]
=== Requester trust

A wallet MUST verify the `COSE_Sign1` and the certificate in `x5chain` with a C2PA COSE verifier.
The end-entity certificate MUST meet the C2PA certificate profile (<<C2PA>>).

*(proposed)* A production wallet MUST also validate the chain against a trust list, normally the C2PA trust list.
A wallet MAY offer a development mode that checks the certificate profile only.
In that mode, the wallet MUST show the person that the requester is not trusted.
_(Traces to `TrustMode::TrustAnchors`, `TrustMode::ProfileOnly`, and `RequesterInfo::trusted`.)_

The wallet SHOULD show the person the requester's certificate subject common name and issuer organisation.
_(The values come from `RequesterInfo`.)_

[[wallet-validation]]
== Wallet validation of a request

Before it asks the person to sign, a wallet MUST perform these checks on a request envelope fetched for an invite.
It MUST reject the request if any check fails.

. The `cose_sign1` is a valid `COSE_Sign1` over `request`, with the external AAD `macawg.sign_request.v1`, under the key of the end-entity certificate in `x5chain`.
. The certificate meets the C2PA certificate profile and, in production, chains to a trust anchor (<<trust-modes>>). Any error the verifier reports is fatal.
. `request` parses as a sign request.
. `type` is `macawg.sign_request`.
. `version` is supported.
. `session_id` equals the invite's `sid`.
. `nonce` equals the invite's `n`.
. The current time is no later than the acceptance deadline (<<acceptance-deadline>>).
. `issued_at` is no later than the current time plus the allowed clock skew.
. `signer_payload.sig_type` is `cawg.identity_claims_aggregation` or `cawg.x509.cose`.
. `signer_payload.referenced_assertions` includes a hard binding assertion.
. `max_signature_size` is greater than 0 and no more than 65536.
. If `requested` is present, `sig_type` is `cawg.identity_claims_aggregation`, and `requested` is well-formed (<<requested>>).
. The `cose_sign1` is tagged, and its protected header `content type` is `application/vnd.macawg.sign-request+json`.
. _(Withdrawn in 0.6; was the `expected_claim_generator` check. The number is kept so later checks do not change.)_
. For HTTPS, `session_url` is present and equals the invite's `u` (<<url-comparison>>).
. If `crit` is present, the wallet recognises and implements every member it names (<<extensions>>).
. *(proposed)* If `response_proof_required` is `true` and the wallet cannot obtain a response proof, the wallet does not offer to sign (<<response-proof>>).
. `issued_at` is earlier than `expires_at`, and `expires_at` is no more than 15 minutes after `issued_at`.
. `signer_payload` contains no member the wallet does not recognise.
. The envelope and its parts are within the limits in <<resource-limits>>. The wallet MUST check the envelope size before it decodes it.

_(Checks 1–14, 16, 17 and 19–21 trace to `open_request` and `check_request`. The size check before decoding traces to `RequestEnvelope::from_slice`. For check 18, the reference implementation provides `SignResponse::check_before_send`, which refuses a `signed` response without a proof; the decision not to offer signing is the application's.)_

[[acceptance-deadline]]
=== Acceptance deadline

The allowed clock skew is 5 minutes.
_(Traces to `CLOCK_SKEW`.)_

The _acceptance deadline_ of a request is `expires_at` plus the clock skew.
It is the single deadline for every party, and every time check in this document uses it:

* the wallet does not offer to sign after it (check 8 above);
* the wallet does not send a `signed` response after it;
* the device does not accept a response after it (<<device-validation>>);
* the device discards the session after it (<<session-state>>).

A request is _expired_ when the current time is later than its acceptance deadline.
Because `expires_at` is at most 15 minutes after `issued_at`, the acceptance deadline is at most 20 minutes after `issued_at`.
_(Traces to `SignRequest::check_not_expired`, used by `check_request`, `SignResponse::check_before_send` and `check_response`.)_

The wallet MUST check the acceptance deadline again immediately before it sends a `signed` response, and MUST NOT send one after it.
The person may take a long time to decide.
_(Traces to `SignResponse::check_before_send`.)_

A wallet MAY decode an unverified request to explain to the person why it was rejected.
It MUST NOT offer to sign one.
_(Traces to `RequestEnvelope::unverified_request`.)_

*(proposed)* After these checks pass, the wallet SHOULD show the person the requester (<<trust-modes>>), the `context`, the roles in `signer_payload.role`, and, for each identity request, its type, fields, `required` flag, and `purpose`.
Before the person agrees, the wallet MUST show the actual identity values that it will disclose, and MUST explain that they will be published in the asset, where anyone who reads the asset can see them.
*(proposed)* The wallet MUST NOT send a signed response unless the person agrees.

[[ica]]
== Identity claims aggregation

This section applies when `signer_payload.sig_type` is `cawg.identity_claims_aggregation`.

=== Unsigned ICA credential

The wallet selects the person's verified identities that answer the request, and builds an unsigned ICA credential.
It has these members:

[cols="2,1,5",options="header"]
|===
|Member |Presence |Meaning
|`signer_payload` |REQUIRED |Copied unchanged from the request.
|`verified_identities` |REQUIRED |A non-empty array of `verifiedIdentities` entries (<<CAWG-IA>> §8.1).
|`max_signature_size` |REQUIRED |Copied from the request.
|`accepted_issuers` |OPTIONAL |Copied from `requested.accepted_issuers`.
|===

Each `verified_identities` entry has `type`, the OPTIONAL fields `name`, `username`, `address` and `uri`, `verifiedAt` (a timestamp), and `provider`, which is an object with `id` (a URI) and `name`.

The wallet MUST NOT build an unsigned ICA credential for a request whose `sig_type` is not `cawg.identity_claims_aggregation`.
`verified_identities` MUST NOT be empty.
If the request has `requested`, then `verified_identities` MUST answer it (<<selective-disclosure>>).
If the request has no `requested`, the wallet chooses which identities to include.
_(Traces to `UnsignedIcaCredential::for_request`.)_

=== Issuance

An ICA issuer that receives an unsigned ICA credential:

. MUST refuse if `accepted_issuers` is non-empty and does not contain the issuer's DID.
. MUST refuse if `signer_payload.sig_type` is not `cawg.identity_claims_aggregation`, or if `verified_identities` is empty.
. MUST check every entry of `verified_identities` against what the issuer itself has verified for the person, and MUST refuse if any entry does not match.
The issuer vouches for every identity in the credential.
. MUST build the credential JSON in <<ica-vc>>, with `validFrom` set to the time of issue.
. MUST sign it as in <<ica-cose>>.
. MUST refuse if the tagged `COSE_Sign1` is longer than `max_signature_size`.

_(Rules 1, 2, 4, 5 and 6 trace to `UnsignedIcaCredential::issue`. Rule 3 is the documented precondition of `issue`. The reference implementation leaves it to the issuer service.)_

[[wallet-release]]
=== Wallet checks before release

The issuer, not the wallet, produces the bytes that the device receives and that the asset publishes.
An issuer could return extra identities or different values.
It could also keep `verifiedIdentities` unchanged and add identifying information elsewhere, such as a stable `credentialSubject.id` or a custom property.
The device's checks (<<device-ica>>) reject identities whose type, fields or provider the device did not request, but only after the device has received them.
The device does not know the exact values the person approved, so it cannot detect a changed value.
Only the wallet's exact-match check (check 2 below) protects the approved values.

The published bytes are the whole tagged `COSE_Sign1`, not only the credential JSON.
COSE headers sit outside the payload and can carry any data (<<RFC9052>> §3).
An issuer could return approved credential JSON together with an identifying header parameter.
It could also add an entry to `@context` or `type` whose URL contains an identifier, because <<CAWG-IA>> §8.1 requires only that those arrays contain at least the expected entries.

Before it sends a `signed` response, the wallet MUST:

. verify the returned credential with the checks of <<device-ica>>;
. check that `verifiedIdentities` is exactly the list the person approved, with the same values;
. check that the credential contains no property outside <<ica-properties>>, at any level;
. check that the `COSE_Sign1` headers and the structural values meet <<ica-cose-profile>>.

If check 1 or 2 fails, the wallet MUST NOT send the credential.
If check 3 or 4 fails, the wallet MUST either refuse to send the credential, or show the person every additional property, header or entry and its value and send it only if the person approves.

The wallet MUST NOT remove or rewrite anything to make a credential pass.
Removing a header or an entry would change the signed bytes, which would break the issuer's signature and the `signature_digest` of any response proof.
The wallet either sends the bytes exactly as issued, or does not send them.

_(Traces to `UnsignedIcaCredential::check_issued`. It compares `verifiedIdentities` with the unsigned credential's list, in order. Checks 3 and 4 are part of check 1, because `verify_ica_credential` rejects any property outside <<ica-properties>> and applies <<ica-cose-profile>>, so the reference implementation always takes the first option for checks 3 and 4: it refuses.)_

[[ica-properties]]
.Permitted ICA credential properties (Macawg restriction)
[cols="2,3",options="header"]
|===
|Object |Permitted properties
|Credential |`@context`, `type`, `issuer`, `validFrom`, `validUntil`, `credentialSubject`
|`credentialSubject` |`verifiedIdentities`, `c2paAsset`
|`verifiedIdentities[]` |`type`, `name`, `username`, `address`, `uri`, `verifiedAt`, `provider`
|`provider` |`id`, `name`
|`c2paAsset` |The members of <<wire-signer-payload>>
|`referenced_assertions[]` |`url`, `alg`, `hash`
|===

<<CAWG-IA>> and the VC data model allow more properties than these.
Macawg narrows the set because every property is published in the asset.

[[ica-cose-profile]]
==== COSE headers and structural values

The allowlist above covers the credential's properties.
These rules cover the rest of the published bytes, and the values of the properties whose content is fixed:

[cols="2,3",options="header"]
|===
|Item |Permitted content
|Protected header |Exactly two parameters: `alg` (1) with value EdDSA (-8), and `content type` (3) with value `application/vc`.
|Unprotected header |Empty.
|`@context` |Exactly `["https://www.w3.org/ns/credentials/v2", "https://cawg.io/identity/1.1/ica/context/"]`, in that order.
|`type` |Exactly `["VerifiableCredential", "IdentityClaimsAggregationCredential"]`, in that order.
|`issuer` |A string: the issuer's DID, with no fragment and no query. Not an object.
|`credentialSubject` |A single object, not an array.
|===

The device SHOULD apply the same rules.
_(Traces to `verify_ica_credential`, so the reference implementation applies them on the device and in `UnsignedIcaCredential::check_issued`.)_

NOTE: The empty unprotected header is a deliberate initial limitation.
It excludes the `sigTst2` time stamp header, which <<CAWG-IA>> §8.1.4 allows.
A time-stamp token carries the time stamp authority's certificates, policy and optional extensions, which need their own privacy assessment before Macawg permits them.

[[credential-status]]
==== Revocation status: a deliberate initial limitation

<<CAWG-IA>> §8.1.2.7 says an identity claims aggregator SHOULD make a credential revocable with a `credentialStatus` entry, preferably a W3C Bitstring Status List entry, and §8.1.5 tells validators how to check it.
This Macawg profile excludes `credentialStatus`.
As a result, it rejects ICA credentials that use credential-level revocation.
This is a deliberate limitation of the first version, not a statement that revocation is unimportant.

Status metadata is not automatically free of information about the person.
A status entry carries a list URL and an index into the list.
A per-person list URL identifies the person.
A sequentially allocated index can reveal issue order and link credentials.
When a validator fetches the status list, the issuer can learn which credentials are being checked, unless the list is large and served as a whole.

A later version may permit a defined status structure, for example:

* exactly one `BitstringStatusListEntry` with `statusPurpose` `revocation`;
* a `statusListCredential` URL that the issuer shares across all its credentials, and that carries no per-person component;
* a `statusListIndex` chosen at random from a list of at least 131,072 entries, the minimum size in the W3C Bitstring Status List specification.

The wallet would then check the entry against this structure before release, in the same way as <<ica-cose-profile>>.

[[ica-vc]]
==== Credential JSON

[source,json]
----
{
  "@context": [
    "https://www.w3.org/ns/credentials/v2",
    "https://cawg.io/identity/1.1/ica/context/"
  ],
  "type": ["VerifiableCredential", "IdentityClaimsAggregationCredential"],
  "issuer": "did:web:ica.example",
  "validFrom": "2026-10-14T09:31:02Z",
  "credentialSubject": {
    "verifiedIdentities": [
      {
        "type": "cawg.social_media",
        "username": "ada",
        "uri": "https://social.example/ada",
        "verifiedAt": "2026-10-01T12:00:00Z",
        "provider": { "id": "https://social.example", "name": "Social Example" }
      }
    ],
    "c2paAsset": {
      "sig_type": "cawg.identity_claims_aggregation",
      "referenced_assertions": [
        {
          "url": "self#jumbf=c2pa.assertions/c2pa.hash.data",
          "alg": "sha256",
          "hash": "gZXc8AkKv86pivdlRBEH0f//JnJJGh5EpjvAZZ+tUcU="
        }
      ],
      "role": ["cawg.creator"]
    }
  }
}
----

This credential answers the example request: one `cawg.social_media` identity with exactly the requested `username` and `uri`, and an issuer in `accepted_issuers`.
The hashes are the request's, in standard base64.


`c2paAsset` is the request's `signer_payload`, but its hashes are standard base64 (<<RFC4648>> §4), not base64url, as <<CAWG-IA>> §8.1 requires.
`role` and `alg` are omitted when absent.
_(Traces to `ica_vc_json`.)_

NOTE: The `@context` URI is the version 1.1 ICA context.
This is the URI that <<CAWG-IA>> 1.3 itself uses, and the one that c2pa-rs validators expect.

[[ica-cose]]
==== Signature

The credential JSON is the embedded payload of a tagged `COSE_Sign1`.
Its protected header has `alg` EdDSA and `content type` `application/vc`.
The signature is Ed25519 over the `Sig_structure` with an empty external AAD.
The tagged `COSE_Sign1` bytes are the identity assertion's `signature` value.
_(Traces to `UnsignedIcaCredential::issue`, `ICA_CONTENT_TYPE`.)_

The issuer's DID MUST be `did:jwk` or `did:web`.
The signing key MUST be a verification method in the DID document's `assertionMethod` relationship (<<CAWG-IA>> §8.1).
For `did:jwk`, the DID document lists the key in `assertionMethod` unless the JWK has `"use": "enc"`.
_(Traces to `IcaIssuer::did` and the `IssuerKeyResolver` contract. *(proposed)* The reference implementation does not reject a `did:jwk` with `"use": "enc"`.)_

NOTE: Implementation compatibility.
c2pa-rs 0.91 decodes `did:jwk` with a padded base64url decoder, so it rejects the unpadded form that did:jwk requires whenever padding would be needed.
The reference implementation works around this by adding `"alg": "EdDSA"` to the JWK, which makes the encoded JWK 93 bytes long, so it never needs padding (`did_jwk_for_ed25519`).
This is a workaround for one validator, not a protocol requirement.

[[issuer-api]]
=== Wallet to issuer interface (informative)

Binding B (<<binding-b>>) proposes a standard interface: OpenID4VCI with the issuance inputs in `authorization_details`.
Its dataset carries the same information as the unsigned ICA credential above, plus the proof requirement.
Until binding B is normative, an issuer interface SHOULD carry the same inputs, and SHOULD apply the same rules.
The issuer API in the companion `macawg-wallet` repository is a draft and is not part of this specification.

[[x509]]
== X.509 signatures

This section applies when `signer_payload.sig_type` is `cawg.x509.cose`.

A request for this `sig_type` has no `requested` member (<<requested>>).

The wallet signs the CBOR `signer_payload` with the person's X.509 credential, as <<CAWG-IA>> §8.2 specifies.
The wallet MUST refuse to send a signature longer than `max_signature_size`.
The wallet SHOULD verify its own signature before it sends the response.
_(Traces to `sign_signer_payload`, `verify_identity_signature`, behind the `x509` feature.)_

[[response]]
== Sign response

=== Structure

The wallet answers with a sign response, a JSON object with these members:

[cols="2,1,5",options="header"]
|===
|Member |Presence |Meaning
|`type` |REQUIRED |The string `macawg.sign_response`.
|`version` |REQUIRED |The protocol version, `1`.
|`session_id` |REQUIRED |Copied from the request.
|`nonce` |REQUIRED |Copied from the request.
|`status` |REQUIRED |`signed` or `declined`.
|`signer_payload` |REQUIRED when `signed` |The payload that was signed. MUST equal the request's `signer_payload`.
|`signature` |REQUIRED when `signed` |base64url of the exact bytes for the identity assertion's `signature` field.
|`reason` |OPTIONAL when `declined` |Text explaining the refusal. At most 256 bytes (<<field-lengths>>).
|`response_proof` |OPTIONAL when `signed` |base64url of a tagged `COSE_Sign1` (<<response-proof>>).
|===

_(Traces to `SignResponse`, `SignOutcome`.)_

*(proposed)* A wallet MUST send `declined` when the person refuses.
It SHOULD NOT put information about the person's identities in `reason`.

[[response-proof]]
=== Response proof

The identity signature covers the `signer_payload`, not the session.
The response's `session_id` and `nonce` are not signed.
If two sessions carry the same `signer_payload`, for example because the device retries after a failure, an earlier valid identity signature can be placed in a response with the new session's identifiers, and the device will accept it.
That preserves the earlier attestation, but it does not show that anyone approved the current request.
Single-use sessions (<<session-state>>) do not prevent this, because the reuse crosses sessions.

When a device needs proof of fresh approval, it uses a response proof: a tagged `COSE_Sign1` made with the same key that made the identity signature.
For ICA, that is the issuer's key, and the wallet passes the request digest to the issuer.
For X.509, it is the person's key.

==== Format

* The payload is embedded. It is the deterministically encoded CBOR map `{ "request_digest": bstr, "signature_digest": bstr }`, with exactly these two keys.
`request_digest` is the SHA-256 of the binding's request representation (<<proof-domains>>). In binding A, that is the request bytes from the envelope.
`signature_digest` is the SHA-256 of the decoded `signature`.
* The external AAD is the binding's proof AAD (<<proof-domains>>). In binding A, it is the ASCII bytes `macawg.sign_response.v1`.
* The protected header's `alg` is the identity signature's algorithm.

_(Traces to `ica_response_proof`, `x509_response_proof`, `RESPONSE_PROOF_AAD`.)_

==== Requesting a proof

The device asks for a proof by setting `response_proof_required` to `true` in the signed request.
It SHOULD also list `response_proof_required` in `crit` (<<extensions>>).

A wallet that receives a request with `response_proof_required` set to `true`:

* MUST NOT send a `signed` response without a `response_proof`;
* if it, or the issuer, cannot produce a proof, MUST tell the person, and MUST answer `declined` with `reason` set to `response_proof_unsupported`.

_(Traces to `SignRequest::require_response_proof`, which also lists the member in `crit`, and to `SignResponse::check_before_send` for the first rule. The second rule is the application's.)_

==== Producing a proof for ICA

The proof is meant to show that the named actor approved this request.
An issuer signature over a digest shows only that the issuer signed it.
So an ICA issuer MUST create a response proof only within an issuance transaction that the named actor has authorized now, for the request digest presented in that transaction.
For example, the actor might sign in again, or confirm on a device the issuer trusts.
A long-lived token that the wallet holds is not enough.
The issuer MUST NOT create a proof for a request digest outside such a transaction.
_(`ica_response_proof` signs the digest it is given, so the issuer service must enforce this rule.)_

==== Validating a proof

The device MUST keep the exact request bytes it placed in the envelope until the session ends.
A device that requires a proof MUST reject a `signed` response unless all of these hold:

. `response_proof` is present, and decodes as a tagged `COSE_Sign1` with an embedded payload.
. The payload is a CBOR map with exactly the keys `request_digest` and `signature_digest`, each a 32-byte byte string.
. `request_digest` equals the SHA-256 that the device computes over its stored request bytes.
. `signature_digest` equals the SHA-256 that the device computes over the decoded `signature` it received.
. The protected `alg` equals the identity signature's algorithm.
. The signature verifies, with external AAD `macawg.sign_response.v1`, under the key that verified the identity signature: the ICA issuer's key, or the key of the X.509 end-entity certificate.

Verifying the proof's signature alone is not enough: checks 3 and 4 bind the proof to this request and to this signature.
_(Traces to `check_response`, which takes the request envelope the device served, and recomputes both digests. It also requires the payload to be exactly the deterministic encoding of the map.)_

A device that does not require a proof MAY ignore `response_proof`.
_(The reference implementation validates a proof whenever one is present, and reports the result in `Accepted::response_proof_verified`.)_
Without the proof, an accepted response shows only that a valid identity signature exists for this `signer_payload`.

The proof is not embedded in the asset, so it does not change the published credential.

=== Example

[source,json]
----
{
  "type": "macawg.sign_response",
  "version": 1,
  "session_id": "q2b9Yv0rN4kM1pQyHk3ZtA",
  "nonce": "8m2cR0xV7JpLwE5uT1aGsQ",
  "status": "signed",
  "signer_payload": {
    "referenced_assertions": [
      {
        "url": "self#jumbf=c2pa.assertions/c2pa.hash.data",
        "alg": "sha256",
        "hash": "gZXc8AkKv86pivdlRBEH0f__JnJJGh5EpjvAZZ-tUcU"
      }
    ],
    "sig_type": "cawg.identity_claims_aggregation",
    "role": ["cawg.creator"]
  },
  "signature": "0oRYJqIBJwN..."
}
----

The `signer_payload` equals the request's, as it must.
The `signature` value is truncated for display; a real response carries the whole credential.

[[device-validation]]
== Device validation of a response

The device MUST perform these checks on a sign response before it uses the signature.
It MUST reject the response if any check fails.

. `type` is `macawg.sign_response`.
. `version` is supported.
. `session_id` and `nonce` equal those of the request the device sent.
. The current time is no later than the request's acceptance deadline (<<acceptance-deadline>>).
. If `status` is `declined`, the session ends without a signature.
. `signer_payload` equals the request's `signer_payload`.
. The decoded `signature` is no longer than `max_signature_size`.
. The `signature` is valid for the `sig_type`: see <<device-ica>> and <<device-x509>>.
. If the request has `response_proof_required` set to `true`, `response_proof` is valid (<<response-proof>>).

_(Traces to `check_response`.)_

[[device-ica]]
=== ICA credential checks

For `cawg.identity_claims_aggregation`, the device MUST check:

. `signature` is a tagged `COSE_Sign1`, as <<CAWG-IA>> §8.1 requires.
. Its protected header has `alg` EdDSA and `content type` `application/vc`. It has no other header parameters, protected or unprotected (<<ica-cose-profile>>).
. The payload is embedded, and parses as credential JSON.
. `@context` contains both `https://www.w3.org/ns/credentials/v2` and `https://cawg.io/identity/1.1/ica/context/`. It contains nothing else (<<ica-cose-profile>>).
. `type` contains both `VerifiableCredential` and `IdentityClaimsAggregationCredential`. It contains nothing else.
. The `issuer`, with any fragment removed, is in `requested.accepted_issuers`, if that list is present and non-empty.
. The issuer's Ed25519 key is resolved from an `assertionMethod` verification method: locally for `did:jwk`, and with a DID resolver for other methods. If the device cannot resolve the key, the check fails.
. The Ed25519 signature verifies with an empty external AAD.
. `validFrom` is present, as <<CAWG-IA>> §8.1 requires for VC 2.0 credentials, and no later than now plus the clock skew. `validUntil`, if present, is no earlier than now minus the clock skew.
. `credentialSubject` is a single object, or an array with exactly one element.
. `credentialSubject.c2paAsset`, with its hashes decoded from standard base64, equals the request's `signer_payload`.
. `verifiedIdentities` is non-empty, and, if the request has `requested`, answers it (<<selective-disclosure>>).

_(Traces to `verify_ica_credential`. Because it applies <<ica-cose-profile>>, it also requires the `@context` and `type` entries in order, rejects an `issuer` with a fragment or query, and accepts `credentialSubject` only as a single object.)_

These checks repeat the issuer's checks.
The device does not trust the wallet to have chosen the identities correctly, nor the issuer to have honoured `accepted_issuers`.

[[device-x509]]
=== X.509 signature checks

For `cawg.x509.cose`, the device MUST verify the signature over its `signer_payload` as <<CAWG-IA>> §8.2 specifies, and MUST check that the signing certificate meets the certificate profile.
The device MAY leave trust in the person's certificate to validators of the asset.
_(Traces to `verify_identity_signature`.)_

=== Use of the signature

After acceptance, the device MUST place the decoded `signature` bytes, unchanged, in the identity assertion's `signature` field.
It MUST place them in the assertion whose `signer_payload` is the request's `signer_payload`.
_(Traces to `Accepted::signature`.)_

[[session-state]]
=== Session state *(proposed)*

The reference implementation is stateless, so the application that runs the session must enforce these rules.

* The device MUST accept at most one `signed` response per session.
It MUST mark the session as finished atomically with accepting the response, so that two concurrent submissions cannot both be accepted.
* A response that fails validation MUST NOT end the session.
Otherwise anyone who can reach the session URL could close the session by posting garbage.
The wallet MAY retry until the acceptance deadline.
The device SHOULD rate-limit submissions per session.
* A valid `declined` response ends the session.
* The device MUST discard the session once it is finished, or once the acceptance deadline has passed (<<acceptance-deadline>>).

[[transport]]
== Transports for binding A

[[transport-https]]
=== HTTPS (normative)

When the invite has `t=https`, the session URL `u` names one resource:

* `GET u` returns the request envelope as `application/json`.
* `POST u` with a sign response as `application/json` delivers the response.

_(Traces to `TransportHint::Https`.)_

*(proposed)* The wallet MUST send the response only to the request's `session_url`, which it has checked equals `u` (<<wallet-validation>>).

*(proposed)* Redirects:

* The wallet MUST NOT follow an HTTP redirect (3xx) in answer to its `POST`.
It MUST NOT send the response body to any URL other than `session_url`, whether automatically or after asking the person.
It MUST treat a redirect as a failed delivery.
* The wallet MUST NOT follow an HTTP redirect in answer to its `GET`, and MUST treat one as a failed fetch.
The request is then always fetched from the URL that the person scanned.

Many HTTP client libraries follow redirects by default, and some resend a `POST` body on a 307 or 308.
Wallets MUST turn this off.

[[url-comparison]]
==== URL comparison

The session URL MUST meet these restrictions:

* It is an absolute URL with the scheme `https`, or `http` in development.
* It has no userinfo component and no fragment.
* It contains only ASCII characters. Hosts are written in their A-label (punycode) form.

The device MUST write the identical string in the invite's `u` and in the request's `session_url`.
It SHOULD write the URL in the form that the WHATWG URL serializer produces, so that parsers that normalize URLs do not change it.

The wallet compares the value of `u` with `session_url`.
It decodes `u` from the query as an `application/x-www-form-urlencoded` value, and takes `session_url` from the JSON string.
The two strings MUST be identical, character for character.
The wallet MUST NOT normalize either string before comparing: no case folding, no removal of default ports, no change to percent-encoding, no trailing-slash change.
A wallet MUST reject a session URL that breaks the restrictions above.

_(Traces to `check_session_url`, called from `Invite::parse`, `seal_request` and `check_request`, and to `check_request` for the comparison. `Invite::parse` keeps the decoded string in `TransportHint::Https`. `check_session_url` also rejects spaces and ASCII control characters, which a URL parser would strip or encode.)_

*(proposed)* The device MUST serve the session URL over TLS, except during development (see <<invite>>).

*(proposed)* The device SHOULD return HTTP 404 or 410 <<RFC9110>> for a session URL that is unknown, finished, or expired.
*(proposed)* The device SHOULD answer a `POST` with 2xx after it accepts the response, and with 4xx after it rejects one, leaving the session open (<<session-state>>).

*(proposed)* The session URL SHOULD NOT contain the nonce, because URLs end up in logs and caches.
The request, which does contain the nonce, is protected by TLS.

[[transport-ble]]
=== Bluetooth Low Energy (placeholder)

When the invite has `t=ble`, the device is a BLE peripheral that advertises the GATT service `svc`, and MAY advertise the local name `name`.
_(Traces to `TransportHint::Ble`.)_

This draft does not define the GATT characteristics, how messages are fragmented, or link security.
A future version will define them.
Until then, BLE is not interoperable.

[[binding-b]]
== Binding B: OpenID4VCI issuance of ICA credentials *(proposed)*

This binding defines how a wallet obtains an ICA credential from an ICA issuer using <<OpenID4VCI>>.
It replaces the informal wallet-to-issuer interface of earlier drafts (<<issuer-api>>).
It does not change the device-facing exchange: the wallet still answers the device through binding A, or through binding C.

Status: proposed. Not implemented. Every identifier in this section is proposed, and its name is a placeholder until a namespace is chosen (<<extension-inventory>>).

=== Roles

[cols="2,3",options="header"]
|===
|Macawg |OpenID4VCI
|Wallet |Wallet, acting as the OAuth client
|ICA issuer |Credential Issuer, with its Authorization Server
|Named actor |End-User who authenticates at the Authorization Server
|ICA credential |Credential, of the format in <<vci-config>>
|===

The person needs only an account at the issuer.
The binding does not need an existing holder-bound credential, or a wallet signing key.
The credential is issued without cryptographic key binding, which <<OpenID4VCI>> §14.2 allows for bearer credentials.
Its binding is to the asset, through `c2paAsset`, not to a holder.

[[vci-config]]
=== Credential configuration

The issuer publishes a credential configuration in its Credential Issuer Metadata (<<OpenID4VCI>> §12.2.4):

[source,json]
----
{
  "credential_issuer": "https://ica.example",
  "credential_endpoint": "https://ica.example/credential",
  "authorization_servers": ["https://ica.example"],
  "credential_configurations_supported": {
    "cawg_ica": {
      "format": "macawg_ica_cose",
      "credential_signing_alg_values_supported": ["EdDSA"],
      "macawg_issuer_did": "did:web:ica.example"
    }
  }
}
----

`format` `macawg_ica_cose` *(proposed)*::
A Credential Format Profile, as <<OpenID4VCI>> Appendix A lets deployments define.
A credential of this format is the tagged `COSE_Sign1` of <<ica-cose>>, meeting <<ica-properties>> and <<ica-cose-profile>>.
In a Credential Response it is the base64url encoding of those bytes, as <<OpenID4VCI>> §8.3 requires for binary formats.

`macawg_issuer_did` *(proposed)*::
The DID that will appear in the credential's `issuer`.

The configuration MUST NOT include `cryptographic_binding_methods_supported` or `proof_types_supported`, so a Credential Request carries no `proofs` (<<OpenID4VCI>> §8.2).

=== Issuer identity: DIDs and HTTPS endpoints

The device trusts ICA issuers by DID (`accepted_issuers`).
<<OpenID4VCI>> identifies a Credential Issuer by an HTTPS URL (§12.2.1).
This binding connects the two without adding a new device-side trust input:

. The wallet chooses an issuer endpoint whose `macawg_issuer_did` is in `accepted_issuers`, or is allowed by the wallet's issuer policy when `accepted_issuers` is empty.
. Unless the metadata is signed (<<OpenID4VCI>> §12.2.3), `macawg_issuer_did` is only a routing hint, protected by TLS.
. The binding is the credential's signed `issuer`. Before release, the wallet MUST check that `issuer` equals the advertised `macawg_issuer_did`, and that it is accepted (<<wallet-release>>).
. For `did:web`, the DID's host SHOULD equal the host of the Credential Issuer Identifier. A wallet SHOULD refuse an issuer where they differ, unless its policy names that pairing.

The device's checks are unchanged: it checks the DID and the signature (<<device-ica>>), and never needs the issuer's URL.

[[vci-dataset]]
=== Issuance inputs: an immutable dataset in `authorization_details`

The wallet must give the issuer the signer payload, the approved identity values, the maximum size, and the proof requirement.
Two designs were considered.

Custom Credential Request parameters (rejected)::
<<OpenID4VCI>> §8.2 allows additional Credential Request parameters, but says the Credential Issuer "MUST ignore any unrecognized parameters".
An issuer that does not implement Macawg would ignore the signer payload and the identities, and issue some other credential.
That fails open, breaking G4, G5 and G12.
The inputs would also arrive only after authorization, so the actor's consent would not cover them.

A dataset prepared before authorization (chosen)::
The wallet puts the inputs in an `authorization_details` object of type `openid_credential` (<<OpenID4VCI>> §5.1.1, <<RFC9396>>).
<<OpenID4VCI>> §5.1.1 lets additional fields be defined for this type.
<<RFC9396>> §5 requires the Authorization Server to reject an object of a known type that has unknown fields, with `invalid_authorization_details`.
So an issuer that does not implement Macawg fails closed.
The Authorization Server shows the dataset to the actor before consent.
It returns the granted `authorization_details` in the Token Response (<<RFC9396>> §7), with `credential_identifiers` (<<OpenID4VCI>> §6.2).
The Credential Request then names a `credential_identifier`, so the issuer issues exactly the authorized dataset.

==== The `authorization_details` object *(proposed)*

[cols="2,1,4",options="header"]
|===
|Member |Presence |Meaning

|`type` |REQUIRED |`openid_credential`.
|`credential_configuration_id` |REQUIRED |A configuration whose `format` is `macawg_ica_cose`.
|`macawg_signer_payload` |REQUIRED |The device's `signer_payload`, in the JSON form of <<wire-signer-payload>>, unchanged.
|`macawg_verified_identities` |REQUIRED |The `verifiedIdentities` entries the person approved, with their exact values.
|`macawg_max_signature_size` |REQUIRED |The device's `max_signature_size`.
|`macawg_accepted_issuers` |OPTIONAL |The device's `accepted_issuers`, if non-empty.
|`macawg_response_proof` |OPTIONAL |Present if and only if the device requires a response proof. An object with `request_digest` (base64url of the 32-byte digest) and `aad` (the device-facing binding's AAD string, <<proof-domains>>).
|===

A receiver MUST reject the object if it contains a member it does not recognise.

Example, as pushed with PAR:

[source,json]
----
[
  {
    "type": "openid_credential",
    "credential_configuration_id": "cawg_ica",
    "macawg_signer_payload": {
      "referenced_assertions": [
        { "url": "self#jumbf=c2pa.assertions/c2pa.hash.data", "alg": "sha256", "hash": "gZXc8AkKv86pivdlRBEH0f__JnJJGh5EpjvAZZ-tUcU" }
      ],
      "sig_type": "cawg.identity_claims_aggregation",
      "role": ["cawg.creator"]
    },
    "macawg_verified_identities": [
      {
        "type": "cawg.social_media",
        "username": "ada",
        "uri": "https://social.example/ada",
        "verifiedAt": "2026-10-01T12:00:00Z",
        "provider": { "id": "https://social.example", "name": "Social Example" }
      }
    ],
    "macawg_max_signature_size": 8192,
    "macawg_accepted_issuers": ["did:web:ica.example"],
    "macawg_response_proof": {
      "request_digest": "uU0nuZNNPgilLlLX2n2r-sSE7-N6U4DukIj3rOLvzek",
      "aad": "macawg.sign_response.v1"
    }
  }
]
----

==== Flow

. The wallet validates the device's request, and the person approves the identities in the wallet (<<wallet-validation>>).
. The wallet sends a Pushed Authorization Request (<<RFC9126>>) with the dataset in `authorization_details`, using the authorization code flow with PKCE (<<OpenID4VCI>> §5).
PAR is REQUIRED in this binding, because the dataset is too large for a URL.
The pre-authorized code flow MUST NOT be used, because the issuer could not then obtain the actor's current authorization for this dataset.
. The Authorization Server:
.. MUST reject the request if any member is unknown, or if `macawg_accepted_issuers` is non-empty and does not contain its DID;
.. MUST authenticate the named actor in this authorization transaction when `macawg_response_proof` is present, and SHOULD do so otherwise. Reusing an earlier session without the actor's action is not enough when a proof is required;
.. MUST check every entry of `macawg_verified_identities` against what the issuer has verified for this actor, and refuse if any differs;
.. MUST show the actor the identity values and the fact that they will be published in an asset, and obtain consent.
. The Token Response MUST return `authorization_details` identical to the pushed object, with `credential_identifiers`.
The Authorization Server MUST NOT narrow or change the dataset, because a changed dataset would not be what the person approved in the wallet.
The wallet MUST compare the returned object with the one it pushed, and stop if they differ.
. The wallet sends a Credential Request with `credential_identifier`, and no other Macawg parameters.
. The Credential Issuer:
.. MUST issue exactly one credential that meets <<ica-vc>>, <<ica-properties>> and <<ica-cose-profile>>, with `c2paAsset` equal to `macawg_signer_payload` and `verifiedIdentities` equal to `macawg_verified_identities`;
.. MUST refuse if the credential is longer than `macawg_max_signature_size`;
.. if `macawg_response_proof` is present, MUST return a response proof (<<response-proof>>) over the given `request_digest` and the issued credential's bytes, with the given `aad`, in the Credential Response parameter `macawg_response_proof` (base64url). <<OpenID4VCI>> §8.3 allows additional Credential Response parameters.
The issuer MUST create the proof only within this authorized transaction;
.. MUST NOT use deferred issuance (<<OpenID4VCI>> §9), because the acceptance deadline is short.
. The wallet decodes the credential and runs the checks of <<wallet-release>>, including the issuer check above.
If a proof is required, the wallet MUST also verify it as the device would (<<_validating_a_proof>>), using the request representation it holds.
. Only then does the wallet send the signed response to the device.

A wallet whose issuer rejects the dataset, or cannot return a required proof, answers the device with `declined`, and `reason` `response_proof_unsupported` where that is the cause.

==== Changes from earlier drafts

Trust model:: Unchanged. The device trusts DIDs; the issuer endpoint is only located by URL.
Privacy:: Unchanged in content: the issuer sees the signer payload hashes and the identities, as before. The dataset now also passes through the Authorization Server.
Cryptography:: Unchanged. The credential and the proof are the same objects.
User experience:: The person authenticates at the issuer for each signing that requires a proof. This was already required by G10.
Wire representation:: Binding A is unchanged. The wallet-to-issuer interface is new; the earlier one was informative only.

[[binding-c]]
== Binding C: OpenID4VP device-to-wallet exchange *(proposed, evaluation)*

This section evaluates carrying the operation over <<OpenID4VP>> instead of binding A.
It defines enough to show which parts reuse standard mechanisms, which need extensions, and which binding A checks need new rules.
It is not ready to be normative (<<recommendation>>).

Status: proposed, for evaluation. Not implemented. Every identifier here is a placeholder (<<extension-inventory>>).

=== Mapping

[cols="2,3,3",options="header"]
|===
|Operation input |OpenID4VP element |Kind of reuse

|Claim generator credential (G1) |Signed Request Object (<<OpenID4VP>> §5, <<RFC9101>>) with `typ` `oauth-authz-req+jwt`, the C2PA chain in `x5c`, and Client Identifier Prefix `x509_hash` (<<OpenID4VP>> §5.9.3) |Profile: the wallet validates `x5c` against the C2PA trust list and certificate profile, not the Web PKI
|Invitation (G3) |QR code with `client_id` and `request_uri` (<<OpenID4VP>> §5.7, §5.10) |Configuration, plus the rules in <<vp-invitation>>
|Nonce, session id |`nonce` and `state` (<<OpenID4VP>> §5.2, §5.3) |Configuration
|Session endpoint |`response_uri` with `response_mode` `direct_post` or `direct_post.jwt` (<<OpenID4VP>> §8.2, §8.3) |Configuration, plus the rules in <<vp-invitation>>
|Deadline (G11) |Request Object `iat` and `exp` |Configuration; the clock-skew rule is Macawg's

`x509_hash` is the base64url SHA-256 of the DER leaf certificate.
The wallet MUST check it against the `x5c` leaf certificate (<<OpenID4VP>> §5.9.3).
Like binding A's `x5chain`, it authenticates the requester (G1); neither binds the requester to the claim's signer (<<claim-generator-substitution>>).

==== Transaction data type `macawg_cawg_sign` *(proposed)*

The decoded entry is a JSON object:

[source,json]
----
{
  "type": "macawg_cawg_sign",
  "credential_ids": ["cawg"],
  "signer_payload": { "...": "as in binding A" },
  "max_signature_size": 8192,
  "requested": { "...": "as in binding A, ICA mode only" },
  "context": { "title": "IMG_0042.jpg" }
}
----

* Its members have the meanings they have in binding A.
* A wallet MUST reject an entry with a member it does not recognise.
* `response_proof_required` is absent, because binding C always requires a response proof (<<vp-authorization>>).
* All Macawg semantics MUST be inside this entry.
OAuth and <<OpenID4VP>> ignore unknown Request Object parameters, so a requirement placed there would fail open.
<<OpenID4VP>> §5.1 requires a wallet to return an error if a request contains an unrecognized transaction data type, so this entry fails closed (G12).

[[vp-authorization]]
=== Which credential authorizes the transaction?

In <<OpenID4VP>>, transaction data is authorized by presenting a credential with Holder Binding.
The wallet includes a representation of the transaction data in that presentation (§8.4), for example `transaction_data_hashes` in an SD-JWT VC Key Binding JWT (Appendix B.3.3.1), or in mdoc `DeviceSigned` (Appendix B.2.1).

Neither mode of Macawg fits that model directly:

ICA mode::
The wallet holds no credential to present.
The ICA credential is issued during the exchange (<<vp-issuance>>), and it is a bearer credential with no holder key (<<binding-b>>).
The only party that can authorize the transaction with a key is the ICA issuer, under current actor authorization.
So in binding C, the representation of the transaction data in the presentation is the response proof, signed by the issuer over the Request Object digest.

X.509 mode::
The person's X.509 key signs both the identity signature and the response proof.
The authorizing credential is the X.509 certificate, presented in the CSC X.509 format (<<binding-d-dmb>>).

Because the response proof is the only thing that binds the result to the transaction, binding C MUST always require it.
Without it, the presentation would carry no representation of the transaction data, which §8.4 requires.

This is a new credential prerequisite only in X.509 mode, where the wallet needs the CSC X.509 format.
ICA mode needs no holder credential, but it needs binding B.

[[vp-issuance]]
=== How the wallet obtains a new ICA credential

Between validating the Request Object and posting the response, the wallet runs binding B.
It builds the dataset from the `macawg_cawg_sign` entry and the person's approval.
`macawg_response_proof.request_digest` is the SHA-256 of the Request Object's compact serialization as received, and `aad` is `macawg.sign_response.oid4vp.v1` (<<proof-domains>>).
The acceptance deadline from the Request Object's `exp` applies to the whole issuance.

Issuance and presentation stay distinct.
Binding B authorizes issuance at the issuer.
Binding C carries the request and the result between device and wallet.
The response proof links the two.

=== How the device gets the exact signature bytes

The DCQL query (<<OpenID4VP>> §6) has one Credential Query with `id` `cawg`.
In ICA mode its `format` is `macawg_ica_cose`; in X.509 mode it is the CSC X.509 format.
The ICA mode query states that no Holder Binding proof is expected.
<<OpenID4VP>> §8.6 allows a request to waive Holder Binding; the exact DCQL parameter for this is not verified in this draft.

The `vp_token` is `{ "cawg": [ <presentation> ] }` (<<OpenID4VP>> §8.1).

* For `macawg_ica_cose`, the presentation is the JSON object `{ "signature": <base64url>, "response_proof": <base64url> }` *(proposed)*.
* For the CSC X.509 format, the presentation is an `x509PresentationResponse` (<<CSC-DMB>> §8.2) with an additional member `cawg` holding the same object *(proposed; needs agreement with CSC)*.

The device decodes `signature` and uses those bytes unchanged (G9).

=== How exact disclosure restrictions are enforced

DCQL selects claims by path and can constrain values (<<OpenID4VP>> §6).
It cannot express "exactly one identity of this type, with exactly these fields and no others", forbid additional properties, or bind the exact values the person approved in the wallet.
So the `requested` member inside `macawg_cawg_sign` remains authoritative, and the wallet and device checks of binding A apply unchanged (<<selective-disclosure>>, <<wallet-release>>, <<device-ica>>).
A DCQL `claims` list MAY mirror `requested` to help generic wallet interfaces, but it is not used for any decision.

`accepted_issuers` also stays in the transaction data.
DCQL `trusted_authorities` (<<OpenID4VP>> §6.1) does not, in the text reviewed, define a type for a list of DIDs.

=== How unsupported requirements are rejected

* An unknown transaction data type: the wallet returns an error (<<OpenID4VP>> §5.1).
* A wallet that does not support `transaction_data` at all rejects the request (§5.1).
* An unknown member inside `macawg_cawg_sign`: the wallet rejects the request (this binding).
* An unsupported credential format: the device's `vp_formats_supported` and the DCQL `format` let the wallet detect it, and it returns an error.
* A required proof that the issuer cannot produce: the wallet returns an error instead of a presentation.

[[vp-invitation]]
=== Invitation-binding checks that need new rules

Binding A puts the nonce in the QR code, and checks that the signed request echoes it.
In <<OpenID4VP>> the QR code carries only `client_id` and `request_uri`, and the nonce is inside the signed Request Object.
These rules replace the binding A checks:

. `request_uri` MUST contain at least 128 bits of entropy, and the device MUST serve it only until the acceptance deadline. It is the invitation secret.
. The `client_id` in the QR code MUST equal the Request Object's `client_id`, including the prefix (<<OpenID4VP>> §5.10.1). The wallet MUST check this.
. The wallet MUST check that the origin of `response_uri`, from the signed Request Object, equals the origin of the `request_uri` it fetched. This replaces the exact `session_url` comparison (<<url-comparison>>), because <<OpenID4VP>> uses two different URLs.
. The wallet MUST NOT follow HTTP redirects when it fetches `request_uri` or posts to `response_uri`.
. The device MUST NOT return `redirect_uri` in its response to the wallet's POST. <<OpenID4VP>> §8.2 says the wallet must follow one when present; in a cross-device flow that would only open a browser on the phone.
. The wallet SHOULD use `request_uri_method` `post` with `wallet_nonce` (<<OpenID4VP>> §5.10), so the Request Object is fresh for this wallet.

<<OpenID4VP>> §14.2 notes that `direct_post` is susceptible to session fixation, and that its response-code mitigation does not apply to cross-device flows.
The relay analysis of <<relay>> applies unchanged: possession of the QR code is not proximity.

=== Trust model, privacy and user experience

Trust model:: The same certificate authenticates the request. The wallet's trust anchors for `x509_hash` requests MUST be the C2PA trust list, not a Web PKI or OpenID Federation anchor.
Privacy:: No new disclosure in ICA mode. `direct_post.jwt` adds response confidentiality beyond TLS.
Cryptography:: The request signature is JWS, not COSE. The proof uses a new AAD (<<proof-domains>>).
User experience:: A generic OpenID4VP wallet cannot complete the exchange. It must implement the Macawg transaction data type and format.

[[binding-d]]
== Binding D: X.509 signing with CSC *(proposed)*

This section covers `cawg.x509.cose` signatures made with a key that the wallet does not hold.
It distinguishes two Cloud Signature Consortium specifications:

* the CSC API (<<CSC-API>>), between a signing application and a remote signing service provider (RSSP), which binding D uses inside the wallet;
* CSC Data Model Bindings (<<CSC-DMB>>), a wallet-facing binding for relying parties, evaluated in <<binding-d-dmb>>.

Local-key signing stays supported and normative: the wallet signs with a key it holds, as <<x509>> describes.

=== Remote signing with `signatures/signHash` *(proposed)*

The wallet builds the CAWG `COSE_Sign1` itself, and asks the RSSP only for the raw signature.

. The wallet builds the `COSE_Sign1` that <<CAWG-IA>> §8.2 specifies for `cawg.x509.cose`, including the protected header, the certificate chain, the payload placement and the external AAD that §8.2 requires.
. It computes `ToBeSigned`, the CBOR encoding of the `Sig_structure` `["Signature1", protected, external_aad, payload]` (<<RFC9052>> §4.4).
. It hashes `ToBeSigned` with the hash the algorithm uses, and calls `signatures/signHash` (<<CSC-API>> §11.10) with that digest in `hashes`, and the `signAlgo` from the table below.
. It converts the returned signature to the COSE form, as the table says.
. It inserts the signature, encodes the tagged `COSE_Sign1`, and verifies it locally with the certificate before release (<<x509>>).

[cols="1,3,2,3",options="header"]
|===
|COSE `alg` |CSC `signAlgo` and parameters |Digest for `hashes` |Conversion to COSE

|ES256 (-7) |`1.2.840.10045.4.3.2`, ecdsa-with-SHA256 |SHA-256(`ToBeSigned`) |DER `ECDSA-Sig-Value` to 64-byte `r‖s` (<<RFC9053>> §2.1)
|ES384 (-35) |`1.2.840.10045.4.3.3`, ecdsa-with-SHA384 |SHA-384(`ToBeSigned`) |DER to 96-byte `r‖s`
|ES512 (-36) |`1.2.840.10045.4.3.4`, ecdsa-with-SHA512 |SHA-512(`ToBeSigned`) |DER to 132-byte `r‖s`
|PS256 (-37) |`1.2.840.113549.1.1.10`, RSASSA-PSS, with `signAlgoParams` for SHA-256, MGF1 with SHA-256, salt length 32 |SHA-256(`ToBeSigned`) |None: the RSA signature is used as is
|PS384 (-38), PS512 (-39) |RSASSA-PSS with the matching hash, MGF1 hash and salt length |SHA-384 or SHA-512 |None
|EdDSA (-8) |Not possible with `signHash` |— |—
|===

ECDSA encoding::
<<CSC-API>> v2.0 does not say how an ECDSA result is encoded.
A wallet MUST accept a DER `ECDSA-Sig-Value` and convert it, and MUST reject a result it cannot convert to the exact COSE length.

RSASSA-PSS salt length::
COSE PS256, PS384 and PS512 use a salt as long as the hash (<<RFC8230>>). The wallet MUST send `signAlgoParams` that say so.

Ed25519::
COSE `EdDSA` (-8) is pure Ed25519 over the whole `ToBeSigned` message; COSE does not use the prehash variant (<<RFC9053>> §2.2).
`signHash` takes a digest.
Ed25519ph over a digest gives a signature that does not verify as COSE -8, and pure Ed25519 over a digest signs the wrong message.
So an RSSP can make a CAWG Ed25519 signature only if its API signs arbitrary `ToBeSigned` bytes.
<<CSC-API>> v2.0 lists no EdDSA algorithm, and `signatures/signDoc` produces AdES formats, not COSE.
Whether later CSC API versions add raw-message signing was not verified for this draft.

==== Authorization

The RSSP authorizes signing for specific digests: `credentials/authorize` takes `hashes`, and OAuth authorization can carry `authorization_details` of type `credential` with `documentDigests` and `hashAlgorithmOID` (<<CSC-API>> §8.4, §11.6).
`signHash` rejects a digest the authorization does not cover.

* The wallet MUST authorize exactly the `ToBeSigned` digest.
* It SHOULD give a `label` that identifies a CAWG identity assertion and the asset's title.
* The RSSP's consent screen shows a digest and a label, not the identity semantics. G6 remains the wallet's job.

==== Response proofs with a remote key

A response proof's `ToBeSigned` includes the digest of the identity signature, which exists only after the first `signHash` call.
Because authorization binds digests in advance, the proof needs a second authorization, which normally means a second user action, unless the RSSP authorizes two signatures without fixed digests.
This is an open issue for binding D: requiring a proof with a remote key costs a second approval.

==== Certificate trust

The certificate must meet <<CAWG-IA>> §8.2 and the validators' trust lists for CAWG X.509 identities.
Qualification for eIDAS QES (`signatureQualifier`) is a separate matter: CAWG validators do not evaluate it.
An RSSP certificate issued for AdES signing might not meet CAWG's X.509 requirements. This draft has not checked that, and a profile must.

[[binding-d-dmb]]
=== CSC Data Model Bindings (informative evaluation)

<<CSC-DMB>> 1.0 lets a relying party ask a wallet, over <<OpenID4VP>>, to create a signature with an X.509 certificate.
It defines:

* the credential format `https://cloudsignatureconsortium.org/2025/x509`, and `x509MetadataQuery` with `certificateFingerprints`, `certificatePolicies` and `keys` for choosing a certificate (§8, §8.1);
* the transaction data type `https://cloudsignatureconsortium.org/2025/qes` with `signatureRequests` (§6.2.1);
* the response `qesResponse`, with `documentWithSignature` or `signatureObject`, as padded base64, inside `x509PresentationResponse.qes` (§6.2.2, §8.2);
* rendering rules for the approval screen (§6.4).

Reusable for Macawg X.509 mode::
The X.509 format identifier and `x509MetadataQuery`, for certificate selection in binding C.
The rendering rules are a useful model for G6.

Not reusable::
The `qes` type is for AdES signatures (`signature_format` C, X, J or P) over documents fetched by `href` or `data:` URL.
It makes `signatureQualifier` mandatory, and so assumes a QES.
It has no COSE output, and no notion of a CBOR `signer_payload`.

Needed extensions::
A transaction data type for CAWG COSE signing (`macawg_cawg_sign`, <<binding-c>>) whose `credential_ids` names the X.509 query, and a new `cawg` member in `x509PresentationResponse`.
That structure belongs to CSC, so the member needs CSC's agreement, or a Macawg-owned format instead.

<<CSC-DMB>> Note 25 says a QES made this way has no Holder Binding and can be replayed.
Macawg's response proof addresses exactly that gap.
<<CSC-DMB>> also says its transaction data types are likely to change (Notes 6, 16 and 18), so a Macawg profile of it should not be normative yet.

== Security considerations

=== Bindings

The considerations below are written for binding A.
They apply to binding C as amended by <<vp-invitation>>, and binding B and binding D keep every guarantee of <<guarantees>> except where their sections say otherwise.
A proof made in one binding never verifies in another, because each binding has its own AAD (<<proof-domains>>).

=== Requester authentication

The device signs every request with its C2PA signing credential.
The wallet verifies the signature against the C2PA trust list before it asks the person anything.
A malicious requester can therefore get a person to sign only if that requester holds a trusted C2PA signing credential.
A development-mode wallet (<<trust-modes>>) loses this property, and must say so.

[[relay]]
=== Binding to the invitation, and relay

The nonce reaches the wallet out of band, through the camera.
Because the device signs the nonce, an attacker cannot pass off a request from another session as the one in the invite.

Scanning an invite proves possession of the invitation, not physical proximity to the device.
Anyone who can see the code can read the nonce.
An attacker does not need to create a signature: they can fetch the device's signed request and relay it.

Two relay attacks follow:

Redirected response::
The attacker shows an invite with the real `sid` and `n`, but with `u` pointing to their own HTTPS proxy.
The proxy relays the device's envelope, receives the identity-bearing response, and forwards it to the device.
The attacker sees the person's disclosed identities.
The `session_url` check (<<_nonce_binding>>) prevents this: the signed request names the device's URL, and the wallet posts only there.
The reference implementation checks `session_url`; posting only there, without following redirects, is the application's job.

Remote invitation::
The attacker shows the device's genuine invite to a person who is not near the device, for example by photographing it.
The `session_url` check does not prevent this, because every message goes to the real device.
Macawg version 1 does not prevent it.
Stronger proximity guarantees need an additional mechanism, such as a short-range transport or a code that the device shows only after the wallet connects.

=== Replay and freshness

Several mechanisms limit replay:

* Requests expire (`expires_at`) and cannot be issued in the future, with a 5-minute skew allowance.
* A response names its session by `session_id` and `nonce`, but these are not signed.
* The identity signature covers the `signer_payload`, so it is valid only with the same referenced assertions, including the same hard binding (<<binding-scope>>).
* *(proposed)* A session accepts at most one `signed` response (<<session-state>>).

The wallet does not sign the response envelope.
An attacker who can inject responses, and who holds an earlier valid identity signature for the same `signer_payload`, can get it accepted in a new session.
That is a replay of an earlier approval, not proof of a new one.
*(proposed)* Devices that need fresh approval MUST use <<response-proof>>.

An attacker who can inject responses can also inject a `declined` response, which denies service but does not cause a false attribution.

[[binding-scope]]
=== What the identity signature binds

The identity signature covers the `signer_payload`: the referenced assertions and their hashes, the `sig_type`, and the roles.
It does not, by itself, cover the rest of the claim.

The required hard binding reference ties the signature to the asset's content.
However, another claim that contains the same referenced assertions could carry the same identity assertion while it changes, adds, or removes assertions that are not referenced.

Referencing an assertion protects that assertion only.
Referencing every assertion that exists today does not stop another claim from adding an assertion, or from changing claim fields that are outside the referenced assertions.

<<CAWG-IA>> 1.2 offered `expected_partial_claim` for whole-claim binding and `expected_claim_generator` for the signing certificate.
Version 1.3 removed both, and states that it defines no mitigation for re-signing by an adversarial claim generator (<<CAWG-IA>> §9.4.7).
So no Macawg binding can offer whole-claim binding, and an implementation MUST NOT claim to.

[[claim-generator-substitution]]
=== Claim generator substitution

The requester's certificate and the claim's signing certificate are not linked cryptographically.
A trusted but malicious C2PA signer could relay another claim generator's `signer_payload` under its own name.
Equally, after the identity assertion exists, any claim generator could put it in a new claim that references the same assertions (<<CAWG-IA>> §9.4.7).

This is unmitigated in Macawg version 1, as it is in <<CAWG-IA>> 1.3.
Earlier drafts of Macawg proposed `expected_claim_generator` (G2) to address it.
CAWG 1.3 removed that field and tells validators to ignore it, so a check made only by the wallet would prove nothing to anyone who later validates the asset: the device chooses the hash it sends.
G2 is therefore withdrawn.

What remains is G1: the wallet still authenticates the requester's C2PA certificate, and can show the person who is asking.
That tells the person who requested the signature, not who will sign the claim.
A future CAWG mechanism for this threat could be adopted as a new guarantee.

=== Issuer trust

The device decides which ICA issuers it trusts by setting `accepted_issuers`.
It checks the issuer DID itself (<<device-ica>>).

An empty `accepted_issuers` makes the device accept any issuer with a valid Ed25519 signature.
Anyone can generate a `did:jwk`, assert arbitrary identity values, and pass every cryptographic check.
A valid signature proves control of a key.
It does not prove that anyone verified the identities.

*(proposed)* A production device MUST apply an issuer trust policy.
The policy is either a non-empty `accepted_issuers`, or another defined trust mechanism that the device enforces itself after it verifies the credential, such as a trust list of identity claims aggregators.
An empty `accepted_issuers` is acceptable in production only when such an independent policy applies.
Without one, it is for development only.

`provider.id` and `provider.name` are statements that the issuer vouches for.
A familiar `provider.id` does not independently prove that the named identity provider took part.

For `did:web` issuers, the security of key resolution is the security of the issuer's web origin.

[[resource-limits]]
=== Resource limits

`max_signature_size` lets the device reserve space in the claim before it has the signature.
A wallet rejects values above 64 KiB, so that a request cannot ask it to produce, and the issuer to sign, an arbitrarily large credential.
_(Traces to `MAX_SIGNATURE_SIZE_LIMIT`.)_

That limit does not bound the other inputs.
These are maximums.
A sender MUST NOT exceed them.
A receiver MUST reject an input that exceeds them, and MUST check sizes as received, before it decodes:

[cols="3,1",options="header"]
|===
|Input |Maximum
|Request envelope, as received |1 MiB
|`signer_payload`, as serialized JSON |32 KiB
|Decoded thumbnail |256 KiB
|Certificates in `x5chain` |10
|`max_signature_size` |64 KiB
|`response_proof`, decoded |1 KiB
|Sign response, as received |128 KiB
|===

[[field-lengths]]
==== Field lengths

[cols="2,3",options="header"]
|===
|Field |Allowed length and content
|`session_id`, `sid` |16 to 64 characters from the base64url alphabet (`A`–`Z`, `a`–`z`, `0`–`9`, `-`, `_`)
|`nonce`, `n` |16 to 64 characters from the base64url alphabet; at least 128 bits of entropy (<<invite>>)
|`reason` |At most 256 bytes of UTF-8
|`version` |The integer `1`
|===

A receiver MUST reject a message in which any of these fields breaks its limit.
Restricting `session_id` and `nonce` to the base64url alphabet also means they never need JSON escapes or percent-encoding.
_(Traces to `check_token` and `TOKEN_LENGTH`, called from `Invite::parse`, `seal_request`, `check_request` and `check_response`, and to `MAX_REASON_SIZE`, checked by `SignResponse::check_before_send` and `check_response`. `Invite::parse` requires `v` to be exactly the string `1`.)_

==== How sizes are measured

* The size of a message "as received" is the number of octets in the HTTP body, or in the reassembled message for another transport.
* The length of a string field is the number of octets in its UTF-8 encoding after JSON unescaping.
* The size of `signer_payload` is the number of octets in its _compact form_: UTF-8 JSON with no insignificant whitespace, in which only `"`, `\` and the characters U+0000 to U+001F are escaped, each with its two-character escape where one exists and as `\u00XX` otherwise.

Senders MUST write all messages in compact form.
Then the `signer_payload` that the wallet echoes has the same size as the one the device sent, whatever order the wallet writes its members in.
_(serde_json's default output, `serde_json::to_vec`, is the compact form; a unit test checks the escapes. `seal_request` writes the request with it and measures `signer_payload` on it. An application that serializes a `SignResponse` itself must use the same function, not a pretty printer.)_

==== Response size guarantee

Any allowed request leads to a `signed` response that fits within the response maximum.
In compact form, the response carries:

* the echoed `signer_payload`, at most 32,768 bytes;
* the base64url `signature`, at most 87,382 characters for 64 KiB;
* the base64url `response_proof`, at most 1,366 characters for 1 KiB;
* the other members and JSON syntax, at most 269 bytes, given the field lengths above. This is the size of `{"type":"macawg.sign_response","version":1,"session_id":"…","nonce":"…","status":"signed","signer_payload":…,"signature":"…","response_proof":"…"}` with 64-character `session_id` and `nonce`, and without the three variable values.

That totals at most 121,785 bytes, which is under 128 KiB (131,072 bytes).
A `declined` response is far smaller: its largest variable part, `reason`, is at most 1,536 bytes in compact form, because each of its 256 bytes takes at most six characters.

Receivers MUST still enforce the response maximum on the actual bytes received.

_(Traces to `MAX_ENVELOPE_SIZE`, `MAX_SIGNER_PAYLOAD_SIZE`, `MAX_THUMBNAIL_SIZE`, `MAX_X5CHAIN_CERTS`, `MAX_RESPONSE_PROOF_SIZE` and `MAX_RESPONSE_SIZE`. `seal_request` refuses to exceed them. `RequestEnvelope::from_slice` and `SignResponse::from_slice` check the received size before decoding, and `open_request` and `check_response` check the parts.)_

The values are still open for discussion.
If one changes, the response maximum must be recalculated.

== Privacy considerations

=== Selective disclosure

The `requested` member, together with rule 4 of <<selective-disclosure>>, means that a wallet discloses only the identity types, fields and providers the device asked for.
The device checks this too, so it will not embed an over-disclosing credential.
By then, though, the device has already seen the information, so the protection that matters is the wallet's own check before release (<<wallet-release>>).

The ICA credential is a single signed document.
Once issued, it cannot disclose less than it contains, and it is embedded in the asset, where anyone who reads the asset can see it.
Selective disclosure therefore happens before issuance, when the wallet chooses the identities.
The `purpose` strings help the person decide.

=== Correlation

Each ICA credential names one asset, so credentials for different assets are different documents.
However, they disclose the same identity values, so they can be linked.
This is the purpose of an identity assertion, and *(proposed)* the wallet SHOULD make it clear to the person.

The ICA issuer learns the `signer_payload` hashes and the identities for every asset the person signs.
*(proposed)* Wallets SHOULD let the person choose their issuer.

=== Request contents

The request `context` can contain a thumbnail of the asset.
Anyone who can fetch the session URL can see it, so *(proposed)* the device SHOULD keep session URLs unguessable and short-lived.

A `declined` response tells the device only that the person refused.

[appendix]
[[comparison]]
== Relationship to OpenID4VP, OpenID4VCI and CSC (informative)

This appendix states where Macawg overlaps existing work and what remains specific to it.
<<compat-matrix>> gives the requirement-by-requirement detail.

=== What is not new

Most of binding A's transport pattern already exists elsewhere:

* <<OpenID4VP>> already has signed Request Objects fetched by reference from a QR code, X.509-authenticated verifiers (`x509_hash`), `nonce` and `state`, and `direct_post` to a `response_uri`.
* <<OpenID4VP>> transaction data (§5.1, §8.4) already lets a verifier ask a wallet to authorize typed data, rejects unknown types, and binds a hash of the data into the presentation with the holder's key.
* <<CSC-DMB>> already uses that mechanism to ask a wallet for a signature made with an X.509 certificate, and returns the signature inside the presentation.
* <<OpenID4VCI>> already defines wallet-driven issuance with rich, consented `authorization_details`.
* <<CSC-API>> already defines remote signing of a digest under per-digest authorization.

=== What Macawg adds

The CAWG-specific contribution is the operation (<<operation>>):

* approval of an exact CAWG `signer_payload`, with unknown members rejected;
* a disclosure profile for credentials that are published inside an asset (G5): exact values, a closed property set, and fixed COSE headers;
* issuance of an ICA credential for one asset, during the exchange, with no holder key;
* a request-to-result proof made with the identity signature's key, over the exact request octets and the exact signature octets (G10);
* the size, deadline and fail-closed rules that make this interoperable.

=== Where the overlap stops

OpenID4VP transaction authorization::
It assumes a presented credential with Holder Binding.
Macawg's ICA mode has none: the result is a newly issued bearer credential, and the authorizing key is the issuer's.
The presentation is evidence for the verifier; Macawg's result is an artifact to embed in an asset.
DCQL cannot express Macawg's exact disclosure rules.

CSC Data Model Bindings::
The closest prior art for X.509 mode.
It is limited to AdES formats and QES, has no COSE output, and notes that its result can be replayed.

OpenID4VCI::
Fits the wallet-to-issuer step closely (<<binding-b>>).
Per-asset inputs need extension fields, and the proof needs an extension response parameter.

CSC API::
Fits remote ECDSA and RSASSA-PSS keys.
It cannot produce CAWG Ed25519 signatures through `signHash`, and a proof costs a second authorization.

So Macawg can reuse a great deal, but no existing specification provides the operation itself.
Bindings B, C and D show how much of the transport can be standard; the operation's guarantees still need the Macawg rules.

[appendix]
[[recommendation]]
== Recommendation on binding status (informative)

Normative now::
The operation (<<operation>>), binding A, and local-key X.509 signing.
These are the parts with a reference implementation and tests.
With G2 withdrawn, nothing in the normative binding is waiting on c2pa-rs.

Proposed, and the next candidate for normative status::
Binding B, OpenID4VCI issuance of ICA credentials.
It uses standard mechanisms with fail-closed extension points, preserves every guarantee, and needs no new credential or key.
It should become normative after one issuer and one wallet interoperate, using the test vectors in <<impl-tasks>>.

Proposed, limited::
Binding D remote signing with `signHash`, for ES256, ES384, ES512 and PS256, PS384, PS512 only.
It cannot support Ed25519, and the response proof costs a second authorization.

Evaluation only::
Binding C (OpenID4VP) and the CSC Data Model Bindings profile.
They need a new transaction data type, a new format or response member, a namespace decision, and review by the OpenID and CSC communities.
A generic OpenID4VP wallet would still not complete the exchange, so binding C does not yet deliver the interoperability that would justify replacing binding A.

This table describes the reference implementation, `macawg` 0.2.0, as updated for draft 0.5 in https://github.com/Cognitive-Proof/macawg/pull/1[Cognitive-Proof/macawg#1].
It separates these categories:

Library::
The crate enforces the rule whenever the named function is used.
Helper::
The crate provides a function, but the rule holds only if the wallet or device application calls it.
Application::
The crate does not help; the application must implement the rule.
Not implemented::
No support yet.
Dropped::
The rule will not be implemented as written, and the specification needs to change.

A helper being available does not mean that a given wallet or device calls it.

== Test vectors

`tests/vectors.rs` in the https://github.com/Cognitive-Proof/macawg[reference implementation] holds the binding A vectors, built from this document's examples:

* the example sign request is exactly the compact-form bytes the device signs, and its base64url hash equals the credential's standard base64 hash;
* the request `COSE_Sign1`: tag, detached payload, empty unprotected header, the protected header bytes `{1: -8, 3: "application/vnd.macawg.sign-request+json", 33: [end-entity, CA]}`, and the `Sig_structure`, rebuilt from <<RFC9052>> §4.4 and verified with the certificate's key;
* the ICA response with a fixed Ed25519 issuer key, which makes it deterministic: `request_digest` `f677b250d6435e6a4b4f9b7b2dc37a31fca7ff52de886bb1b27e22d422949520`, the credential's `signature_digest` `a34808a0ef04192a70f929b2d9ade91b9cdcfeaa8aeab5227b76eb713b3d45aa`, the proof payload, its protected header `a10127`, its `Sig_structure`, and the whole proof, whose SHA-256 is `134537d511c85538a379c4ac3d0b36df7b127f3c45ee52a5044e03c8b8ad895f`;
* the X.509 response proof, checked structurally because the person's key is generated;
* domain separation: a proof made with AAD `macawg.sign_response.oid4vp.v1` does not verify under binding A;
* a request whose `signer_payload` carries `expected_claim_generator` is rejected.

A later draft may copy these values into this appendix.
`tests/exchange.rs` and `tests/end_to_end.rs` cover full exchanges.

The reference tests also cover an end-to-end exchange with the checks implemented, and these rejection cases.
All but the redirect case are already tests in the reference implementation: `tests/exchange.rs`, `tests/vectors.rs`, and the unit tests in `src/seal.rs`, `src/ica.rs`, `src/invite.rs` and `src/request.rs`.
Redirect handling belongs to the application's HTTP client.

0.6-draft::

* Recorded the binding A test vectors in the reference implementation (<<test-vectors>>).

0.5-draft::
* Separated the CAWG operation, its inputs, result and guarantees G1 to G12, from its transport (<<operation>>).
* Named the existing exchange binding A, and kept it normative and unchanged on the wire.
* Defined request representations and AAD domains for the response proof (<<proof-domains>>).
* Added binding B, OpenID4VCI issuance of ICA credentials, with an immutable dataset in `authorization_details` (proposed).
* Added binding C, an evaluation of OpenID4VP for the device-to-wallet exchange (proposed).
* Added binding D, remote X.509 signing with the CSC API, and an evaluation of CSC Data Model Bindings (proposed).
* Rewrote the comparison appendix; added the compatibility matrix, extension inventory, recommendation and implementation tasks.

COSE header and structural-value profile, `credentialStatus` limitation, field lengths and size measurement, one acceptance deadline, implementation status by support category.
